# Windows recovery and local drafts

Source checkpoints for [#1473](https://github.com/bipe-chat/bipe/issues/1473) and [#1474](https://github.com/bipe-chat/bipe/issues/1474), part of #1346/#1345. Kotlin/native tests are authored but uncompiled and unrun. MZ's no-build/no-push hold stays active. Windows remains planned; Mac feature work stays paused under ADR0288.

`PendingDeviceRecovery` accepts only a pending, journaled-discard or revoked slot. It reads the current record under an exclusive lease before destructive work. `restorePendingForLogout` restores the existing pending session for `Client.logout`, without sync or automatic cross-signing/backup setup. It never becomes a linked account. A successful logout is persisted as `StoredRecord.Discarding(remoteEnded = true)` before native teardown and key/file removal. Late credential callbacks cannot overwrite that record. A retained native cleanup failure keeps its lease until explicit retry completes.

Local forgetting is separate. Its confirmation explains that local data removal does not prove server logout and asks the person to check Linked devices on the phone. Its journal has `remoteEnded = false`. A missing token does not prove server absence. Likewise, a crash between server acknowledgement and journal commit leaves an unresolved pending record. Recovery never treats an expired/invalid token as a confirmed logout. A cleanup journal can resume without a new login, and a committed revocation tombstone allows key/file cleanup retries. Missing keys or corrupt records do not trigger silent new stores or arbitrary deletion. Linked slots are always refused by this pending recovery API.

`AccountDrafts` binds one writer to one account's SDK client. `SdkComposerDraftStore` calls `Room.loadComposerDraft`, `saveComposerDraft` and `clearComposerDraft`. The pinned Rust implementation writes composer drafts through the SQLite state store's encrypted key/value serializer when the store has its configured key. Bipe's Windows key remains in Credential Manager and is passed to the SDK builder. There is no second local draft file or custom cipher. Bipe core's `draft_from_event` parses assistant-room events, so it is not used for ordinary composer persistence.

The writer coalesces queued edits by room and retains a room model across view closures. Loading must succeed before editing; unsupported reply/edit/attachment drafts stay intact. Save failures keep the current text and offer retry. The draft is cleared only after SDK queue acceptance and only when its revision still matches the submitted text. A later edit away and back to identical text has a different revision and stays in the composer. SDK Markdown construction and send failures leave the existing draft available.

Accepted writes run in a separate owned worker so cancelling room/UI tasks cannot lose the final edit. Account teardown closes the queue, drains writes and retries failed latest values before releasing the native client, encrypted-store key or slot lease. Persistent failure retains those resources in the existing cleanup registry. That worker has no selected-account lookup and never borrows another account's paths or client. Different accounts with identical room IDs keep different queues and stores.

Fifteen synthetic state tests cover recovery isolation/journals/failures/leases and draft coalescing/drain/retry/revisions/reopen/load failures. They are test source, not passing CI evidence. Still required: actual Windows SDK draft save/reopen, DB/WAL plaintext absence and wrong-key tests, real pending/duplicate-device logout/restart, released-phone device evidence, native error/a11y behavior, and exact-head Windows/Android/all applicable CI gates after the hold is lifted.

Provenance: own Windows storage/lifetime/phone-link code; own Mac `MacDrafts.swift`; own Android `ComposerSupport.kt`; bipe-shared `composer` and `desktop-pending-link`; pinned Apache Matrix SDK `Client.restoreSession`, `Client.logout`, Room composer-draft FFI and SQLite state-store serialization. No Element source or new cryptography.
